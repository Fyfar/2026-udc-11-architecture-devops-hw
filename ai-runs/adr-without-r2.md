# ADR-0007: Нагадування й автоматичне повернення незабраних посилок

**Статус:** Запропоновано · **Дата:** 2026-10-27

Спершу я прочитав код `app/`, бо від нього залежить половина рішення. Нижче кожен факт із коду має посилання, а мої припущення позначені **[П]**.

---

## Контекст

### Як це працює зараз (з коду)

- **Реєстрація посилки.** `registerParcel` створює запис зі статусом `waiting`, полем `arrivedAt` і 6-значним кодом (`src/parcels.js:35-56`).
- **SMS про прибуття.** Worker раз на 10 с бере пачку з 50 посилок, у яких `notifiedAt` порожній (`src/worker.js:8-9, 23-38`). SMS шле поза з'єднанням із БД, а потім ставить `notifiedAt`. Отже, доставка «щонайменше один раз»: якщо процес впаде між відправкою і записом, SMS піде повторно. Ліміт провайдера — 5 SMS/с, при відповіді 429 клієнт повторює спробу з backoff (`src/sms.js`).
- **Повернення через 72 год.** Цим займається **нічна** cron-задача `bin/expire-parcels.js`. Звідси кілька проблем:
  1. Посилка повертається не через 72 години, а через 72–96 годин.
  2. `markReturned` викликається **до** `courier.requestReturn` (`bin/expire-parcels.js:14-15`). Якщо API кур'єра впаде, посилка вже позначена `returned`, а кур'єр про неї не дізнається. До того ж виняток перериває цикл, і решта посилок не обробляється.
  3. Подія `returned` у таблицю подій не пишеться, хоча для `picked_up` пишеться.
- **Гонка при видачі.** `pickup` спершу шукає посилку, а потім **безумовно** оновлює статус (`src/parcels.js:61-66`). Тому одна посилка може отримати і `returned`, і `picked_up`. Поки повернення відбувається вночі, це рідкість. Але щойно межа 72 год стане точною, ці дві операції будуть регулярно перетинатися.
- **Комірок у моделі немає.** Є лише `lockerId`, тобто номер поштомата. `sender` — це вільний рядок, і окремого API, де відправник бачить статус, немає.
- **Документація відстала від коду.** `docs/ARCHITECTURE.md` (v1.5) пише про опитування кожні 30 с і 4-значний код. Насправді в коді 10 с і 6 цифр, а пакет має версію 1.7.3.
- **Інфраструктура.** Одна VM, `docker compose` (`api`, `worker`), PostgreSQL на тій самій VM. Залежностей npm немає взагалі.

### Припущення

- **[П1] Що означає «рівно 72 години».** Для мешканця це жорстка межа: о `arrivedAt + 72h` код перестає працювати, хоч би коли спрацював фоновий процес. Для решти системи (запит кур'єру, статус для відправника) достатньо, щоб усе сталося протягом ≤ 1 хв після межі.
- **[П2] Як «звільняється» комірка.** Фізично комірка звільняється лише тоді, коли кур'єр забирає посилку. О 72:00 вона стає недоступною для мешканця і резервується для кур'єра. Повністю вільною вона стає після того, як кур'єр підтвердить, що забрав посилку: його сканер викличе наш API так само, як зараз викликає `POST /parcels`.
- **[П3] Де відправник бачить статус.** У системі служби доставки. Ми передаємо їй статус через наявний `POST /returns`, а потім через підтвердження збору. Окремого публічного трекінгу для відправника в нас немає, і в цьому ADR ми його не робимо.
- **[П4] Відлік часу.** 24, 48 і 72 години рахуються від `arrivedAt` (коли посилку поклали в комірку), а не від `notifiedAt`.
- **[П5] Нічні SMS.** Нагадування надсилаються за розкладом, зокрема вночі, бо так сформульована вимога. Якщо знадобиться «тиха година», це окрема зміна.
- **[П6] Ідемпотентність кур'єра.** API кур'єра ідемпотентний за `parcel_id`, тож повторний запит не створить другого повернення.
- **[П7] Кількість worker'ів.** Worker працює в одному екземплярі. Попри це, рішення має бути безпечним і для кількох екземплярів.

---

## Рішення

**Розклад зберігається в PostgreSQL у вигляді часових міток. Його виконує наявний worker, який опитує базу. Запит до кур'єра йде через outbox-таблицю. Межу 72 год перевіряє також `pickup`.**

### 1. Дані

```sql
ALTER TABLE parcels
  ADD COLUMN return_due_at      timestamptz,   -- arrived_at + 72h, ставиться при реєстрації
  ADD COLUMN reminder1_sent_at  timestamptz,
  ADD COLUMN reminder2_sent_at  timestamptz,
  ADD COLUMN return_started_at  timestamptz,
  ADD COLUMN collected_at       timestamptz;   -- кур'єр забрав → комірка вільна
CREATE INDEX ON parcels (return_due_at) WHERE status = 'waiting';

CREATE TABLE courier_outbox (
  id bigserial PRIMARY KEY, parcel_id bigint NOT NULL UNIQUE,
  next_attempt_at timestamptz NOT NULL DEFAULT now(), attempts int NOT NULL DEFAULT 0,
  sent_at timestamptz, last_error text
);
```

Статуси: `waiting → picked_up` або `waiting → returning → returned`. Тут `returning` означає, що код уже недійсний, а комірка чекає кур'єра. `returned` означає, що кур'єр посилку забрав.

`return_due_at` зберігається явно, а не обчислюється щоразу. Так строк можна змінити окремій посилці (наприклад, продовжити), і для нього можна зробити індекс.

### 2. Жорстка межа в `pickup` (закриває гонку)

```sql
UPDATE parcels SET status = 'picked_up', picked_up_at = now()
WHERE code = $1 AND status = 'waiting' AND now() < return_due_at
RETURNING id, locker_id;
```

Це одна атомарна умовна операція замість теперішньої пари «знайти, потім оновити». Якщо повернення вже почалося, оновиться 0 рядків, і API відповість 404. Так виконується [П1], навіть якщо worker відстає.

### 3. Один цикл worker'а, кроки в порядку пріоритету

1. **Повернення.** В одній транзакції:
   ```sql
   WITH due AS (SELECT id FROM parcels WHERE status='waiting' AND return_due_at <= now()
                ORDER BY return_due_at LIMIT 50 FOR UPDATE SKIP LOCKED)
   UPDATE parcels p SET status='returning', return_started_at=now() FROM due WHERE p.id=due.id
   RETURNING p.id;
   ```
   У тій самій транзакції додаються рядки в `courier_outbox` і подія `return_started`. Зовнішніх викликів усередині транзакції немає.
2. **Outbox кур'єра.** Worker бере рядки, у яких `sent_at IS NULL AND next_attempt_at <= now()`, і поза з'єднанням викликає `courier.requestReturn`. Після успіху ставить `sent_at`. Після помилки збільшує `attempts`, записує `last_error` і відкладає наступну спробу з експоненційним backoff. Помилка однієї посилки не зупиняє обробку решти.
3. **SMS про прибуття.** Як зараз.
4. **Нагадування.** Для кожного з двох нагадувань використовується така схема: спершу посилка «займається» короткою умовною операцією, потім надсилається SMS, і лише якщо SMS не пішло, позначка знімається:
   ```sql
   UPDATE parcels SET reminder1_sent_at = now()
   WHERE id=$1 AND status='waiting' AND reminder1_sent_at IS NULL AND now() < return_due_at
   RETURNING ...;
   ```
   Під час надсилання з'єднання не тримається, тож інваріант із `test/worker.test.js:17` зберігається. Умова на статус гарантує, що нагадування не піде людині, яка вже забрала посилку. Порядок тут навмисно інший, ніж у SMS про прибуття. Дубль SMS про прибуття нешкідливий, а нагадування після видачі посилки збиває з пантелику.
   - **Правило «тільки останнє».** Якщо worker простояв і одночасно настав час обох нагадувань, надсилається лише друге, а перше позначається пропущеним. Якщо до повернення лишилося менше ніж 1 год, нагадування не надсилається зовсім.
   - **Текст нагадування.** Він містить номер поштомата, код і крайній час у часовому поясі `Europe/Kyiv`, наприклад: «Нагадування: посилка у поштоматі №4, код 222222. Заберіть до 30.10 14:05, далі її повернуть відправнику».

Цикл засинає на 10 с лише тоді, коли **жоден** крок не набрав повної пачки. Усі SMS проходять через один клієнт `sms`, тому спільний ліміт 5/с зберігається. Повернення стоять першими, бо від них залежить коректність. Нагадування стоять останніми, бо їх можна відкласти.

### 4. Збір кур'єром і статус для відправника

Додається `POST /parcels/:id/collected`. Його викликає сканер кур'єра з тією ж автентифікацією, що й `POST /parcels`. Виклик переводить посилку з `returning` у `returned` і ставить `collected_at`: з цього моменту комірка вільна. Статус для відправника передається службі доставки через outbox [П3].

### 5. Що відбувається з наявним

- **Нічний cron вимикається.** Скрипт `bin/expire-parcels.js` лишається для ручного запуску і викликає ту саму функцію, що й worker.
- **Міграція.** Заповнюється `return_due_at = arrived_at + 72h`. Посилки, яким на момент розгортання вже більше 72 год, worker поверне на першому ж циклі. Через правило «тільки останнє» не буде лавини подвійних нагадувань.
- **Час і тести.** Усі порівняння часу виконуються через `now()` у БД, тобто за одним годинником. В in-memory сховищі `src/db.js` з'являються відповідні методи, а `clock` передається ззовні, як зараз, тож тести можуть «перемотувати» час.
- **Моніторинг.** Worker щоциклу логує `overdue_returns`: кількість посилок у статусі `waiting`, у яких `return_due_at < now() - 5 min`. Якщо значення більше нуля, worker стоїть, і це привід для алерту. Так само логується розмір незакритого outbox.
- **Документація.** Треба оновити `docs/ARCHITECTURE.md`: 10 с, 6 цифр, нічної задачі більше немає.

### Розглянуті альтернативи

**A. Частіший cron (наприклад, `* * * * *`) з тим самим `expire-parcels.js` і окремою задачею для нагадувань.**
- *Плюси:* мінімум змін. Модель уже знайома. Логіка повернень відокремлена від worker'а.
- *Мінуси:* точність обмежена хвилиною, а без перевірки в `pickup` [П1] однаково не виконується. Запуски можуть накладатися один на одного (потрібен lock або `flock`). Кожен запуск стартує Node і пул з'єднань заново. Cron живе на хості поза `docker compose`, тож це ще одна точка налаштування й моніторингу. Задача «мовчки не запустилася» гірше помітна, ніж зупинений worker. Головне: ця альтернатива не виправляє ні неатомарність `pickup`, ні порядок «позначити, потім викликати кур'єра», тож outbox і умовні оновлення однаково довелося б робити.
- *Висновок:* відхилено. Вона дає лише частину вигоди за ту саму складну частину роботи.

**B. Черга з відкладеними повідомленнями (Redis + BullMQ або RabbitMQ з delayed exchange): при реєстрації ставимо три відкладені задачі на +24, +48 і +72 год.**
- *Плюси:* точність до секунд. Готові механізми повторних спроб і dead-letter. Добре масштабується на багато worker'ів.
- *Мінуси:* новий stateful-сервіс на одній VM, який треба бекапити, моніторити й оновлювати. Проєкт зараз узагалі без залежностей npm. Розклад живе у двох місцях (БД і черга): коли посилку забирають, задачі треба скасувати або перевіряти статус під час виконання. Продовжити строк чи змінити правило для вже поставлених задач складно. Якщо Redis втратить дані, нагадування й повернення втратяться мовчки. Наш обсяг (десятки чи сотні посилок на день) такого не потребує.
- *Висновок:* відхилено. Варто переглянути, якщо з'являться кілька VM або тисячі посилок на годину.

**C. Таймери в процесі (`setTimeout` на 24, 48 і 72 год при реєстрації).**
- Перезапуск чи деплой губить усі таймери, тож без відновлення з БД це не працює. А з відновленням із БД це вже вибране рішення, тільки складніше. Відхилено.

**D. Окрема загальна таблиця `scheduled_actions(parcel_id, kind, due_at, done_at)` замість колонок у `parcels`.**
- *Плюси:* кількість нагадувань і їхні інтервали можна налаштовувати без міграцій, а одна черга обслуговує всі типи дій.
- *Мінуси:* для зміни статусу потрібен join, легше отримати розбіжність між `parcels.status` і розкладом, коду більше.
- *Висновок:* поки відкладено. Якщо інтервали стануть налаштовуваними, перехід буде механічним.

## Наслідки

**Позитивні**
- Межа 72 год точна для мешканця й захищена від гонок: одна посилка більше не може бути і виданою, і поверненою.
- Повернення і статус для відправника з'являються за ≤ 1 хв, а не до 24 год.
- Збій API кур'єра більше не губить повернення і не блокує інші: є повторні спроби й видимий `last_error`.
- Нової інфраструктури немає. Розклад зберігається там же, де дані, з тими самими бекапами і транзакціями.
- Поведінку легко тестувати з підставним годинником.

**Негативні та ризики**
- Worker стає критичним для коректності, а не лише для SMS. Якщо він стоїть, повернення не оформлюються, хоча код однаково перестає працювати завдяки `pickup`. Тому потрібні алерт на `overdue_returns` і `restart: unless-stopped` у compose.
- Нагадування мають дубльний ризик, протилежний SMS про прибуття. Якщо процес упаде між «зайняти» і «надіслати», нагадування може не прийти (at-most-once). Для нагадування це прийнятно, для SMS з кодом ні, тому там залишається at-least-once.
- Опитування додає навантаження на БД: кілька запитів по індексу раз на 10 с. Для одного поштомата громади це незначно.
- Новий статус `returning` змінює значення поля для споживачів `GET /admin/parcels`. Старі записи `returned` лишаються з колишнім значенням («оформлено», без підтвердження збору).
- Залежність від [П2] і [П6]: потрібні виклик `collected` від сканера кур'єра та ідемпотентність `POST /returns`. Якщо служба доставки цього не підтримує, комірка звільнятиметься вручну через персонал, а повтори з outbox можуть створювати дублі повернень.
- Нагадування вночі [П5] можуть викликати скарги. Тиха година додасть правило «перенести до 08:00, але не пізніше `return_due_at − 1h`».

**Попутно помічене, поза межами цього ADR:** якщо в запиті немає `sender`, `registerParcel` падає на `sender.trim()` (`src/parcels.js:42`) і повертає 500 замість 400.
